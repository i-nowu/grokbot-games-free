# SFCで大変だったところ（仕様・環境構築）

## 1. エミュレーターを画面なしで動かす
- **大変だったこと:** GB版ではPyBoy、FC版ではFCEUXのスクリプト機能で通しテストを自動化できました。SFCには、そのまま使えて画面なしで動かせるエミュレーターが、パッケージで入りませんでした。
- **乗り越え方:** snes9xを、ほかのプログラムから呼び出せる部品の形でソースからビルドしました。そのうえで、ボタン入力、スクリーンショット、メモリの読み出しを台本のように書いて流せる、小さなテスト用の仕組みを自前で作りました。ウィンドウを開かないので速く、120フレームを0.2秒ほどで動かせます。
- **GB・FCとの違い:** GBとFCは既存のツールを組み合わせるだけでしたが、SFCではテストの土台そのものを作る必要がありました。

## 2. 日本語の文字
- **大変だったこと:** 開発ライブラリの文字表示は英数字しか扱えません。セリフは数百種類の漢字とかなを使うので、全部の字をVRAMに入れるわけにもいきません。
- **乗り越え方:** 台本や決まった文言（起動時の注意文、コマンド名など）から実際に使う字だけを拾い出して、8x8の字のタイルにするスクリプトを作りました。使う字は330字、VRAMは約5KBに収まっています。フォントに無い字があると、そこでエラーにして止まるようにしました。台本を直したら流し直すだけで済むので、ミニゲームの文字を後から足したときもそのまま追加できました。
- **GB・FCとの違い:** GB・FCは字数が少なく、表示に必要な字を手で用意すれば足りました。SFCは文章量の多いアドベンチャーなので、字の拾い出しを自動にしないと回りませんでした。

## 3. 音の確認
- **大変だったこと:** 自動テストでは音を捨てていたので、曲が本当に鳴っているかを確かめられませんでした。曲データを直接WAVにした試聴用の音では、SFCの音源を通したときの鳴り方は分かりません。
- **乗り越え方:** テスト用の仕組みに録音の機能を足して、実際のROMを動かしたときの音をそのままWAVに録れるようにしました。録った音の大きさを数字で確かめたところ、タイトル曲の途中に不自然な無音が見つかりました。原因は、楽器に音量を保つ設定がなかったことでした。音楽担当が直したあと録り直して、無音がほぼ無くなったことを確かめました。
- **GB・FCとの違い:** FC版では音源のレジスタを読んで「鳴っているか」を確かめました。SFCは音を専用のCPU（SPC700）が鳴らしているので、出てきた音そのものを録って調べるほうが確実でした。

## 4. ビルドの細かいつまずき
- 開発ライブラリのビルドの仕組みとMakefileで、同じ名前の変数がぶつかって、リンクに失敗することがありました。呼び出し方を分けて避け、メンバーにも伝えました。
- 通しテストは、テスト側の時間制限で途中で打ち切られることがありました（FC版で経験済み）。そのため、時間に余裕を持たせて流すようにしています。

## まとめ
SFCは表現力が高いぶん、文字と音の扱いが重くなりました。「画面を見る」「メモリを読む」「音を録る」を自動で流せる仕組みを先に作っておいたことで、ほかの担当の確認やまちがい探しにも使えました。
